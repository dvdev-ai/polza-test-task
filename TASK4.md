# Задача 4 — вайбкод / LLM-стек

Писал сам, без ИИ. Коротко и по делу.

## IDE и модели

Сейчас основной контур: **Cursor** + сильная reasoning-модель на сложные куски (архитектура, баги, данные) и более быстрая модель на рутину (правки UI, мелкий рефактор). Параллельно держу терминал и иногда Claude Code, если нужен длинный автономный прогон по репо.

Полгода назад чаще сидел в VS Code / обычном чате и копировал куски руками. Сейчас почти всё через агента в IDE: он видит файлы, терминал и дифф, меньше теряется контекст.

## Подписки

На полноценную работу обычно хватает:

- Cursor Pro (или аналог с нормальным лимитом агента)
- одна сильная API/чат-подписка на пиковые задачи
- иногда отдельно — хостинг/бот-токены по проектам, это уже не LLM

Если считать только LLM/IDE: ориентир **1–2 платные подписки в месяц**. Третья уже редко окупается, если нет параллельных тяжелых проектов.

## Как сравниваю модели и инструменты

Не по ощущению «красиво ответила», а на одном и том же мини-наборе:

1. разобрать кривые данные / найти аномалию
2. сделать рабочий скрипт загрузки в БД
3. починить один реальный баг с воспроизведением
4. собрать маленький UI поверх данных

Смотрю: сколько правок до рабочего результата, ломает ли соседний код, врет ли в README, проходит ли ручная проверка. Если модель быстро красиво пишет, но падает на втором прогоне — для меня это минус.

## Какие тесты потребую для новой функции

Минимум:

- happy path
- пустые / кривые входные данные
- граничные значения (рейтинг, счетчики, уникальные ключи)
- проверка, что секреты не утекли в клиент
- если есть БД — хотя бы один интеграционный сценарий «загрузил → прочитал»

Для UI еще: поиск/фильтр реально меняют выборку, а не только верстку.

## Разрешения coding-агенту

Дам: чтение репо, правки кода, запуск тестов, локальный docker/compose, миграции в **локальную** БД.

Не дам без явного ок: прод-секреты, прод-БД, force-push, удаление томов/данных, оплату/биллинг, рассылку наружу.

Правило: агент предлагает разрушительное действие — я подтверждаю отдельно.

## Автотесты и CI/CD

Пишу автотесты там, где есть логика и риск регрессии (парсинг, валидация, SQL-слой). На чисто версточных страницах — точечно.

Перед merge/deploy хочу минимум:

- lint / typecheck
- unit/integration на критичный путь
- сборка проходит
- для сервисов с БД — миграции применяются на чистой базе
- не мержим, если красный CI или в диффе есть `.env` с секретами
